# Deploying LUMEN on Render + Neon + Vercel

The [main README](README.md) describes the AWS target: EKS, ALB, RDS,
ElastiCache, S3 + CloudFront. This guide is the managed-platform alternative —
no AWS account, no Kubernetes, and a live URL in about an hour.

| Piece | Runs on | Cost |
|---|---|---|
| Postgres | Neon | free tier |
| Redis (BullMQ + cache) | Render Key Value | free tier |
| `Lumen-backend` (NestJS) | Render Web Service, Docker | free tier |
| `Lumen-Web` (Vite SPA) | Vercel | free tier |
| `Ai-Service` (FastAPI + YOLO) | Google Cloud Run | ~free at low traffic — [step 6](#6-the-ai-service--on-cloud-run) |
| `Lumen-app` (Expo) | EAS build | free tier |

The AI service is the one piece that cannot go on a free 512 MB instance —
PyTorch does not fit — which is why it lands on Cloud Run rather than beside the
backend. See [step 6](#6-the-ai-service--on-cloud-run).

Three files drive this and are already in the repo:

- [`render.yaml`](render.yaml) — the backend and Redis, as a Render Blueprint
- [`Lumen-Web/vercel.json`](Lumen-Web/vercel.json) — SPA routing and cache headers
- [`Lumen-backend/deploy/cloudrun/deploy-ai.sh`](Lumen-backend/deploy/cloudrun/deploy-ai.sh) — the AI service

## Do the steps in this order

The dependencies are circular in one place, so the order matters:

```
1. Neon           → gives you DATABASE_URL
2. Supabase       → gives you SUPABASE_URL + SUPABASE_ANON_KEY  (boot requirement)
3. Render         → needs both of the above; gives you the backend URL
4. Vercel         → needs the backend URL; gives you the web origin
5. back to Render → set FRONTEND_URL to the web origin, or CORS blocks everything
```

Step 5 is the one people forget. The backend cannot know the web app's origin
until Vercel has assigned it, so CORS is necessarily configured after the fact.

## 1. Postgres on Neon

1. Sign up at [neon.tech](https://neon.tech) with GitHub.
2. Create a project — pick the region closest to your users (`ap-south-1`
   Mumbai or `ap-southeast-1` Singapore for India).
3. Copy the **pooled** connection string. It looks like:

```
postgresql://user:password@ep-xxx-pooler.ap-south-1.aws.neon.tech/neondb?sslmode=require
```

Keep `?sslmode=require` — Neon rejects plaintext connections and Prisma will
fail to connect without it.

> **Which connection string?** Use the pooled one (it has `-pooler` in the
> host). The backend runs migrations at boot, and Prisma Migrate needs a direct
> connection for its advisory lock — if migrations hang, switch `DATABASE_URL`
> to the unpooled string, let the deploy finish, then switch back.

Neon's free tier autosuspends the database after ~5 minutes idle. The first
request afterwards pays a second or two of wake-up. That is expected, not a bug.

## 2. Supabase

The backend's env validation (`server/config/env.validation.ts`) refuses to boot
without `SUPABASE_URL` and `SUPABASE_ANON_KEY`, and `SUPABASE_URL` must parse as
a URL. Only the health probe reads them today, but the process exits without
them.

Create a free project at [supabase.com](https://supabase.com) and copy the
project URL and the **anon/public** key from Settings → API. The anon key is
designed to be public; do not use the service-role key here.

## 3. Backend + Redis on Render

1. Sign up at [render.com](https://render.com) with GitHub and grant access to
   `Samartha120/LUMEN-development`.
2. **New → Blueprint**, select the repo. Render reads
   [`render.yaml`](render.yaml) and proposes `lumen-backend` and `lumen-redis`.
3. It prompts for every `sync: false` variable. Fill them in:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the Neon string from step 1 |
| `SUPABASE_URL` / `SUPABASE_ANON_KEY` | from step 2 |
| `FRONTEND_URL` | put `http://localhost:5173` for now — corrected in step 5 |
| `AWS_REGION` / `AWS_BUCKET_NAME` | S3 bucket for complaint photos ([step 7](#7-s3-for-complaint-media)) |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | IAM user keys — Render has no instance roles |
| `SMTP_*` | Gmail app password, or a Resend/Mailgun SMTP endpoint |
| `GOOGLE_MAPS_API_KEY` | restricted key for geocoding |

`JWT_SECRET` and `FASTAPI_API_KEY` are generated by Render — leave them alone.
`REDIS_URL` is wired to the Key Value instance automatically.

4. Apply. The first build takes 5–10 minutes: it compiles native modules
   (`bcrypt`), generates the Prisma client, and builds Nest.

`RUN_MIGRATIONS_ON_START=true` is set in the blueprint, so the schema is created
on first boot. That is the documented single-instance shortcut — **turn it off
the moment you run more than one instance**, or replicas race each other on
Prisma's advisory lock and the rollout stalls.

Verify:

```bash
curl https://lumen-backend-XXXX.onrender.com/api/v1/health
```

`{"status":"ok"}` or `"degraded"` means the API is up (degraded = Redis
unreachable, which still serves traffic by design). A 503 means Postgres is
unreachable — recheck `DATABASE_URL`.

Interactive API docs land at `/api/docs`.

> **Free instances sleep.** After 15 minutes without traffic a free Render
> service spins down, and the next request waits ~50 seconds for a cold start.
> Fine for a demo, wrong for a viva or a live audience — upgrade that one
> service to Starter for the day, or hit the health endpoint on a schedule.

## 4. Web console on Vercel

1. Sign up at [vercel.com](https://vercel.com) with GitHub, **Add New →
   Project**, import the repo.
2. Set **Root Directory** to `Lumen-Web`. This is the only setting you must
   change by hand — the repo has four projects in it and Vercel guesses wrong.
   Framework, build command and output directory come from `vercel.json`.
3. Add an environment variable:

```
VITE_API_BASE_URL = https://lumen-backend-XXXX.onrender.com
```

No trailing slash. Leave `VITE_WS_URL` unset — Socket.IO falls back to the same
origin.

4. Deploy.

> **This URL is compiled in, not read at runtime.** Vite inlines
> `VITE_API_BASE_URL` into the bundle. Changing the backend address means
> triggering a new Vercel deploy — editing the variable alone changes nothing
> until a rebuild happens.

## 5. Close the CORS loop

Copy the Vercel domain and set it as `FRONTEND_URL` on the Render service
(Environment → edit → save; Render restarts automatically).

It is a comma-separated allow-list, so keep local dev working too:

```
https://lumen-web.vercel.app,http://localhost:5173
```

If you test Vercel preview deployments, add those origins as well — each preview
gets its own domain, and one missing entry blocks every request from it.

The symptom of getting this wrong is unmistakable: the site loads, and every API
call fails in the browser console with a CORS error while the same request
succeeds from `curl`. The mobile app is unaffected — native builds send no
`Origin` header.

## 6. The AI service — on Cloud Run

**The rest of the platform runs without it.** `FASTAPI_INFERENCE_URL` is read
per-request rather than at boot, so with the AI service absent the backend stays
healthy and only the detection endpoints fail. Deploy it whenever you are ready.

This one does not go on Render, for one blunt reason: **it needs ~2 GB of RAM.**
Importing `torch` costs around 300 MB before an image is decoded; with the model
loaded and one inference in flight it sits near 1 GB. Render's free and Starter
instances are 512 MB and get OOM-killed during startup, and the 2 GB Standard
plan bills ~$25/mo whether or not anyone uses it.

Cloud Run fits the workload's actual shape. Inference is idle almost all the
time and bursts when someone submits a photo — scale-to-zero means an idle
service costs nothing, and memory is configurable well past 2 GB.

### Prerequisites

- A GCP account with billing enabled (new accounts get $300 in trial credit)
- `gcloud` CLI: `brew install --cask google-cloud-sdk`, then `gcloud auth login`
- **Your trained `best.pt`**, placed at
  `Lumen-backend/server/ai/python/models/best.pt`

That last one is not optional. The service raises in its FastAPI lifespan hook
when the weights are missing, which crashes the worker at boot rather than
serving a model-less container — deploying without them just produces a crash
loop. The deploy script checks for the file first and refuses to start a build.

### Deploy

```bash
cd Lumen-backend
PROJECT_ID=your-gcp-project \
FASTAPI_API_KEY=$(openssl rand -hex 32) \
  ./deploy/cloudrun/deploy-ai.sh
```

Save that generated key — you need the identical value on the backend. The
script builds with Cloud Build, so no local Docker daemon is involved, and
prints the service URL and the two variables to set on Render when it finishes.

Then on the Render backend, set:

```
FASTAPI_INFERENCE_URL = https://lumen-ai-xxxx-el.a.run.app
FASTAPI_API_KEY       = <the same key>
```

Verify before wiring it up:

```bash
curl https://lumen-ai-xxxx-el.a.run.app/health
# {"status":"healthy","model_loaded":true,"device":"cpu",...}
```

`"status":"degraded"` means the process is up but the model did not load.

### Two decisions the script makes, and why

**Weights are baked into the image, not downloaded at startup.** `MODEL_URL` and
`MODEL_S3_URI` exist so a retrained model can roll out without a rebuild — the
right trade for long-lived pods. Cloud Run scales to zero, so every cold start
would re-download the file and charge that latency to a real user request.
Baking it in trades rebuild-on-retrain for a fast, dependency-free cold start.
The weights stay gitignored; there is no `.dockerignore`, so the build context
picks them up.

**`FASTAPI_API_KEY` is mandatory here, not optional.** On EKS this service is a
ClusterIP with no route in from outside, so running keyless is defensible. A
Cloud Run service is on the public internet. It has to be deployed
`--allow-unauthenticated` because the backend authenticates with
`Authorization: Bearer $FASTAPI_API_KEY` and cannot present a Google-signed ID
token — so that shared secret is the only thing in front of the service. The
script refuses to deploy without one. (`/health` stays open by design, so
uptime checks work; it exposes nothing but load state.)

### Cost

Cloud Run bills per request, with a monthly free allowance covering CPU-seconds,
memory-seconds and requests. At demo and project-review traffic this lands at or
near zero. Confirm the current free-tier figures on Google's pricing page rather
than trusting a number here — they change.

`--max-instances 3` is a deliberate ceiling: it caps the blast radius if the
endpoint is ever hammered, since the API key is the only gate.

### Cold starts

An idle service takes roughly 20–40 seconds on its first request while the
container starts, imports torch and loads the model. `--cpu-boost` is set to cut
this down. If a live demo makes that unacceptable, set `--min-instances 1` for
the day — it keeps one warm instance and does bill continuously.

## 7. S3 for complaint media

Photo uploads still go to S3; there is no managed equivalent in this stack.

1. Create a bucket (e.g. `lumen-smartcity-storage`) in your region.
2. Create an IAM **user** — not a role — and attach a policy limited to
   `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on
   `arn:aws:s3:::your-bucket/*`. Nothing wider.
3. Put the access key and secret into the Render environment.

These static keys are exactly what the AWS deployment avoids by using IRSA. They
are the accepted trade-off for running outside AWS — which is why the policy
should be scoped as narrowly as possible. Rotate them if they ever leak into a
log or a screenshot.

If you would rather avoid AWS entirely, Cloudflare R2 and Supabase Storage are
both S3-compatible, but the S3 client is not currently configured for a custom
endpoint, so that needs a small code change first.

## 8. Mobile app

```bash
cd Lumen-app
npx eas login
npx eas build --platform android --profile preview
```

Set `EXPO_PUBLIC_API_URL` to the Render backend URL in `eas.json` or the EAS
project secrets. Like the web app, Expo inlines it at build time — a release
build must be rebuilt when the backend moves.

## When something breaks

**Every browser request fails with CORS, but `curl` works.** `FRONTEND_URL` does
not contain the exact origin. Scheme and host must match exactly, no trailing
slash. Step 5.

**Backend exits immediately on deploy.** Read the first lines of the Render log.
`❌ Invalid environment variables` means Zod rejected something — usually a
missing `SUPABASE_URL`, or a `DATABASE_URL` that does not parse as a URL.

**Health check returns 503.** Postgres is unreachable. Check `?sslmode=require`
is present and that the Neon project is not suspended or deleted.

**Deploy succeeds but the app hangs on first load.** The free instance was
asleep. Wait ~50 seconds.

**Migrations hang during boot.** Prisma's advisory lock over a pooled connection.
Switch `DATABASE_URL` to Neon's unpooled string, deploy once, switch back.

**Web app 404s on refresh at `/app/dashboard`.** The `vercel.json` rewrite is not
being applied — check the project's Root Directory is `Lumen-Web`.

**Render rejects the blueprint on the `lumen-redis` service.** Render renamed
Redis to "Key Value". If your account validates against the older spec, change
`type: keyvalue` to `type: redis` in [`render.yaml`](render.yaml) — the rest of
the block is identical.

**Cloud Run deploy fails "container failed to start and listen on PORT".** The
model did not load within the startup window, or the container OOMed. Check
`gcloud run services logs read lumen-ai --region asia-south1` — a
`FileNotFoundError` means the weights were not in the image, and a silent kill
means raise `--memory`.

**AI endpoints return 401 from the backend.** `FASTAPI_API_KEY` differs between
the Cloud Run service and Render. They must match exactly.

**AI service exits with `FileNotFoundError`.** No weights at `MODEL_PATH` and
neither `MODEL_URL` nor `MODEL_S3_URI` is set. The message names which. On Cloud
Run this means `models/best.pt` was missing from the build context.

## What this costs to run

| | Free tier | Card required? | If you outgrow it |
|---|---|---|---|
| Neon | 0.5 GB storage, autosuspends | no | ~$19/mo |
| Render Key Value | 25 MB | no | ~$10/mo |
| Render backend | sleeps after 15 min idle | no | $7/mo (Starter, always on) |
| Vercel | 100 GB bandwidth | no | $20/mo |
| Cloud Run (AI) | ~180k vCPU-s + 360k GiB-s/mo | **yes** | pay-per-use beyond it |

**Steps 1–5 cost nothing and need no payment method.** That is Postgres, Redis,
the API and the web console — a working, publicly reachable LUMEN. Do those
first; they are the whole platform except inference.

Cloud Run is the only piece that wants a card on file, and Google requires a
billing account even to stay inside the free allowance. At the script's 2 vCPU /
2 GiB that allowance works out to roughly 25 hours of *active* compute per month
— vCPU-seconds run out before memory does — and scale-to-zero means an idle
service burns none of it. Comfortable for a demo, and nothing to pay if you stay
under.

Two options if you would rather not attach a card at all:

- **Skip the AI service.** The backend stays healthy without it; only the
  detection endpoints fail. Everything else works.
- **Run it locally when you need it.** `docker compose up fastapi` in
  `Lumen-backend`, expose it with a tunnel (`cloudflared`, `ngrok`), and point
  the deployed backend's `FASTAPI_INFERENCE_URL` at that URL. Free, and fine for
  a live demo where your laptop is in the room. Not something to leave running.

Hugging Face Spaces is **not** an option here despite the free 2 vCPU / 16 GB
CPU Basic hardware: Docker and Gradio Spaces now require a paid PRO plan on
personal accounts. Only Static Spaces are free.

Plan names and limits change — treat the figures above as a starting point and
confirm current pricing before you commit.
